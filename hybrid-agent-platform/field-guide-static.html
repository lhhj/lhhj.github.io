A data-centre chip in a laptop: what RTX Spark changes for one user and for the enterprise

Since mid-October 2026, Windows laptops have shipped with NVIDIA's Grace Blackwell superchip, the same class of silicon as the DGX Spark desktop. They can run large language models with no cloud connection at all. This article looks at what that makes possible, where it falls short, and how one user's laptop can work with an organisation's on-premises GPU servers and a frontier model in the cloud, based on a hybrid system we built and tested.

1A new kind of laptop

For three years, running a capable language model meant one of two things: renting one in the cloud, or buying a server. RTX Spark adds a third option that fits in a bag.

The chip behind it, GB10, combines an Arm CPU and a Blackwell GPU that share one pool of memory. Until this autumn it shipped only in the DGX Spark, a compact Linux desktop for AI developers. Under the name RTX Spark (chip N1X, co-designed with MediaTek), NVIDIA and Microsoft have now put it into Windows laptops and small desktops.[1] It comes in two versions. The full chip pairs a 20-core CPU with a 6,144-core GPU and 24 to 128 GB of memory. A lighter, laptop-only version has 18 CPU cores, 5,120 GPU cores and 24 or 32 GB.[2]

What matters most is not the core count but the memory. A conventional laptop GPU has 8 to 24 GB of its own memory, and a model must fit there to run quickly. Here the GPU draws on a large share of a single pool, so models that until recently needed a server or a workstation now fit in a laptop. Six manufacturers shipped first models in October, at prices that put them firmly in the premium class.

2What fits, and how fast it runs

Two properties decide what a laptop can do with a model. Memory decides whether the model fits at all. Memory bandwidth decides how quickly it writes, because every generated word requires reading the model's active weights once. That is why mixture-of-experts models suit this hardware so well: they hold a great deal of knowledge but use only a small fraction of it for each word.

The first independent measurements bear this out. Windows Central measured 49 tokens per second for Llama 3.1 8B on a 128 GB Surface Laptop Ultra, with the first word appearing after 0.4 seconds. That is faster than most people read. NVIDIA reports 84 tokens per second for its 24 GB Nemotron 3.5 Bolt, a 74-billion-parameter model compressed to two bits and designed for exactly these machines. Artificial Analysis ran a complete local agent task with Qwen3.8 27B in under 19 minutes. As a general computer the laptop is solid rather than exceptional: its CPU scores between Qualcomm's Snapdragon X Elite and Apple's M4 Max, and its graphics are comparable to an RTX 4070.[5],[7],[8]

3One user: an AI workstation that travels

For an individual, the main change is independence. Capable models no longer need a network connection, a subscription or a data-processing agreement. In its review, Windows Central had the Hermes agent tidy a downloads folder and build a small website with Qwen3.8 27B running entirely on the laptop, without using a single cloud token.[5]

This changes everyday work in practical ways. Drafts, source code and client documents are processed on the device, which makes questions about where data is sent much simpler. Work continues on a plane, at a client site or on an isolated network. Routine drafting, coding and summarising carry no per-token bill. Developers also gain a quieter advantage: the laptop runs the same CUDA software as a DGX Spark or a data-centre GPU, so a prototype built on the train can move to a server without being rewritten.

The limits are just as real. Even the best local models still trail frontier models on difficult reasoning, so a sensible setup keeps a cloud model available for the hard steps and asks before sending anything to it. The 24 and 32 GB configurations are restricted to small or heavily compressed models. Agent software is young: one reviewer could not get OpenClaw to connect at all.[5] And NVIDIA's "all-day" battery claim had not been independently measured under AI load in any review we found.[9] For home users, NVIDIA's free PAIR software can share local inference between several PCs, but its list of supported hardware does not yet name RTX Spark.[10]

4The enterprise: one user, three places to compute

In an organisation, the laptop does not become part of a shared compute pool. Nobody wants a colleague's job running on their battery, and a laptop is too often asleep, on a train or out of reach to be relied on by others. Its role is narrower and more useful: it is the user's own AI workstation, which handles everything that fits on it, and their front end to two larger places to compute that the organisation provides.

The first is the organisation's on-premises GPU servers: DGX Spark units or a private AI cloud with models too large for any laptop, and agents that sit beside shared company systems such as the document archive or the ERP. The second is a frontier model in the cloud, for the hardest reasoning on material the data rules allow to leave. A gateway, run by the organisation, decides for each request where it may go.

We built and tested this pattern as a reference system. Agents open a connection out to the gateway and wait for work on it, so no firewall needs to let anything in. In the first live test on 3 November 2026, Claude Sonnet 5.5 orchestrated an agent that read four sample contracts with a 3-billion-parameter model on a local GPU. Across its first two requests Claude received 5.8 KB, consisting of document IDs, a health report and tool descriptions. A scan of the hub's request log found no text from any of the four contracts.

The laptop does what fits. The building does what's confidential. The cloud does only what's hard and allowed.

For the organisation this has four benefits. Data protection can be shown, not just promised: documents are read where they are stored, and only fields from a schema the organisation defined reach the cloud, which makes GDPR and NIS2 data-flow documentation shorter and checkable. Cost falls in two places. Everyday work on the laptop carries no per-token bill, and the cloud model reads findings rather than documents; in our illustrative calculation (section 7) it reads about 19 times fewer tokens across 200 documents. The on-premises servers can be sized for the large jobs only, because the laptops absorb the small ones. Users keep working during an outage or on the road. And because the laptop runs the same CUDA software as the servers, a team can prototype on the laptop and move the workload to a DGX Spark cluster or a private AI cloud such as HPE Private Cloud AI without starting again.[11]

5Where one request runs: laptop, on-premises or cloud

Each request a user makes has to go somewhere. The decision depends on four questions, asked in order: is the laptop connected, does the task fit on the laptop, is the material confidential, and does the task need frontier-level reasoning? The gateway asks them for every request and logs the answer. Fig. 4 steps through four typical requests.

Two details make this work in practice. First, the confidential path never passes through the cloud: when a laptop hands a job to the on-premises GPUs, the documents travel over the corporate network, and the gateway only issues the instruction and logs it. Second, the questions are written in terms of data classification and zone, not individual models. A rule such as "confidential material may only be processed in the on-premises zone" holds whichever model is fashionable next year. The classification can come from the document's own sensitivity label, from rules, or from a small local router model, and it can only ever be raised. The gateway refuses a route that breaks the rule, and the refusal is logged.

6Architecture choices for the Hugging Face integration

Our reference build uses Hugging Face in three roles. It hosts the hub itself as a Docker Space. It offers Hugging Face Inference Providers as one of the frontier-model options. And it runs a smolagents research agent as a separate Space that, like every other agent, connects out to the hub. For a pilot, this is hard to beat: a public HTTPS endpoint, secrets management and container builds come free, and the whole system can be online in minutes. Moving to production, however, means making several decisions explicitly.

Hosting and availability. A free CPU Space pauses after 48 hours without visitors, and every change to its secrets or hardware restarts the app.[12] When the hub restarts, each agent's connection drops; agents reconnect automatically, but jobs in flight are lost. The hub also keeps its register of connected agents in memory, so it runs as a single instance. A production hub therefore belongs on paid hardware with sleep disabled, or on Azure Container Apps or an on-premises DMZ. It also needs a shared register, such as Redis, before it can run as more than one instance.

Exposure and identity. Claude connectors and remote agents can only reach a hub with a public HTTPS address. A private Space requires a Hugging Face token on every request, which conflicts with connectors that cannot add headers. The reference build therefore uses a public Space protected by its own hub and agent tokens. That is adequate for a pilot but not for an enterprise, which should add single sign-on through an identity-aware proxy, give each agent its own token, and rotate them.

Where inference happens. Hugging Face's router sends each request to the fastest available third-party provider unless a provider is pinned with a suffix on the model name.[13] Each provider has its own data terms and locations. For workloads with residency requirements, the safer choices are a dedicated Hugging Face Inference Endpoint (AWS eu-west-1 in Ireland is the listed EU region, with a private-network option through AWS PrivateLink) or Claude through Amazon Bedrock with an EU geography. Claude in Microsoft Foundry is currently offered as Global Standard or US Data Zone deployments, so it does not by itself keep inference in the EU.[14],[15],[18]

Agents in Spaces belong to the public zone. The research agent runs outside the organisation and reads arbitrary web pages, which may contain instructions aimed at AI systems. It should never receive confidential input, and the gateway should enforce that by zone rather than rely on the model's judgement. Its outputs deserve the same schema discipline as on-premises results.

7Tokens saved: where the savings come from

The economic case for hybrid AI rests on one observation: a frontier model is billed by the token, and most tokens in a document-heavy workflow are document text. If the cloud model reads every contract, invoice or log file, its bill grows with the size of the archive. If it reads only short, structured findings produced on local hardware, its bill grows with the number of decisions instead.

Under these assumptions the hybrid design sends the frontier model about 19 times fewer input tokens at 200 documents. The ratio is not a constant of nature, though. It is roughly the size of a document divided by the size of a finding, and several factors move it in practice.

Short documents shrink the gain. Tickets and e-mails of a few hundred tokens leave little to save, while long contracts, manuals and log archives save the most. Conversations grow. Every model turn resends the conversation so far, so a cloud-only design that has read ten documents pays for them again on every later turn, which makes the real gap larger than a single-pass estimate. Tool descriptions are not free. Each turn includes the description of every available tool, and with dozens of connected agents this overhead can rival the findings themselves. The gateway should offer each conversation only the tools that are relevant to it. Caching narrows the gap. Prompt caching, offered by the major providers, makes a repeated prefix much cheaper, which softens the cost of a cloud-only design that rereads the same material.

Local inference is not free either. It is paid up front, in hardware, power, device wear and the staff time to run it. A fair comparison is monthly cloud savings, the difference in tokens multiplied by the provider's price, set against the hardware cost spread over its useful life plus operations. The hub already records input and output tokens for every conversation, so this can be measured on real workloads rather than estimated. The figure that matters is cost per completed task at equal accuracy. A hybrid design that saves tokens but needs more human review has not saved anything.

8How sovereign is sovereign enough?

"Sovereign AI" is used to mean very different things, from choosing an EU cloud region to running entirely disconnected. It helps to treat sovereignty as a ladder and to decide, use case by use case, which rung is needed. Each step up gives more control and requires more operational work, and above a certain point it costs model capability.

Location is not the whole story. Keeping inference inside the EU is a meaningful step. Amazon Bedrock, for example, offers an EU geography for Claude and pins some models to a single region.[18] Claude in Microsoft Foundry is currently offered as Global Standard or US Data Zone deployments, so it does not by itself keep inference in the EU.[15] Some organisations also weigh the provider's legal jurisdiction, not only where its servers stand. That is a policy and legal question each organisation must answer with its own advisers.

The prompt itself is data. In the hybrid design the documents stay home, but the user's question and the agents' findings go to the frontier model. A question such as "summarise the dismissal case against our employee in Aarhus" contains personal data before any document is read. The gateway should therefore classify prompts as well as documents, and route sensitive conversations to a local orchestrator, which is level 3 on the ladder.

Open-weight models make level 3 realistic, with a gap. The strongest open-weight models of 2026 come close to proprietary frontier models on many benchmarks, and models of that class run on clusters of a few DGX Sparks or on a private AI cloud. They still trail on the hardest planning tasks, and every model has its own licence terms that must be checked. Running them also makes the organisation responsible for updates, evaluation and security patches.

Sovereignty includes the supply chain and the ability to keep working. Model files downloaded from the Hugging Face Hub should be pinned to a specific version, checked against a hash and mirrored internally, like any other software dependency. Operational sovereignty means staying able to work if a cloud provider is unavailable, changes terms or raises prices. A hub that can switch its orchestrator from a cloud model to a local one, as the reference build can, keeps that option open without redesigning the system.

In practice most organisations will not choose one rung for everything. Public research can use level 0 or 1, routine document work fits level 2, personnel and legal matters belong at level 3, and a few environments, such as defence, critical infrastructure and some health data, need level 4. The value of a gateway that routes by data classification is that one platform can serve all of them, and an auditor can see which rule sent which request where.

9The realistic setup: everything on-premises, laptops optional

The figures so far place the frontier model in the cloud. For many organisations that is the step they cannot take. Public bodies, health providers, defence suppliers and firms bound by client confidentiality often need the planning model itself inside their own walls. In that setting the realistic design looks different. The frontier-class model runs on the organisation's own GPU servers, the gateway sits in the data centre or a Kubernetes cluster, and agents run next to the systems that hold the data: ERP, document management, file shares. RTX Spark laptops become an optional extra for field and offline work rather than the backbone. The cloud is still there, but only for work classified as public.

The model is the expensive part. Open-weight models now reach frontier class, but they are large. Moonshot's Kimi K3 has 2.8 trillion parameters, of which about 104 billion are active per token. Its weights ship in MXFP4 and total about 1.56 TB, so it needs roughly 2 TB of GPU memory once working memory is included. In practice that means two 8-GPU H200 servers; a single 8-GPU HGX H200 system is priced at $320,000 to $420,000.[19] Open models in the 300–700-billion-parameter class fit one 8-GPU node, at some cost in planning quality. A DGX Spark cluster is the right home for the 20–120-billion-parameter workers that read the documents, not for the planner.

The laptops become optional. Once the agents run beside the data systems, no laptop has to hold the data. RTX Spark machines are still useful for people who work offline or travel with sensitive material, and they join the same control bus as any other agent. On Arm-based Windows, GPU access inside Docker containers is not documented, so the practical layout is the model running natively on the laptop and only the agent in a container.

What the reference build needed. Checking the build against this design exposed five gaps, all now closed. The hub could hold only one self-hosted model; it now reads any number of models from a configuration file, each tagged with a zone: cloud or on-premises. It had no routing rules; every conversation now carries a classification, and confidential conversations are refused by cloud models and never offered Hugging Face agents, in the chat, the API and the MCP connection alike. A hub in the cloud could not reach an on-premises model without opening a port; a small relay agent beside the GPU server now dials out and forwards requests. Thinking models such as Kimi return their reasoning in a separate field and expect it back during tool use; the hub now passes it through. And the laptop profile now runs the model on the host rather than in a container.

The same code therefore covers every rung of the sovereignty ladder. A cloud hub with on-premises agents sits at level 2. A cloud hub that uses an on-premises model through the relay keeps confidential conversations at level 3. A hub, model and agents that all run inside the organisation, with the cloud switched off, approach level 4.

NVIDIA's secure-agent stack. At GTC in March 2026, NVIDIA announced an Agent Toolkit with three parts: OpenShell, a runtime that sits between an agent and the machine and enforces policy from outside the agent process; NemoClaw, a reference stack that runs agents inside OpenShell with one command; and the AI-Q blueprint for organising agent tasks.[20],[22] Because control sits outside the agent, a prompt injection that takes over the agent still cannot open a network connection the policy forbids. NVIDIA is working with Cisco, CrowdStrike, Google and Microsoft Security on compatibility with their tools.[20] Its own documentation is candid about maturity: NemoClaw is in active development, describes a single-host workflow, and "is not a hardened, multi-tenant enterprise control plane". Fleet-wide policy, central audit export and single sign-on are still manual or on the roadmap.[21] It is a sound sandbox for each agent today, not yet the management layer for a fleet.

Two decisions, two layers. Gateways route by rules: model name, fallbacks, load and budget. Two judgements need more than that, and they should not be made by the same component. The first is how sensitive a conversation is, which decides which models may see it. The second is which of the permitted models should answer, which is a trade-off between cost and capability. The reference build gives the first to a small router of its own, top left in Fig. 8, and the second to NVIDIA NeMo Switchyard.

The router decides sensitivity. It works by three rules that keep it safe. Fixed patterns, such as personal ID numbers, pay or health terms, run first and cannot be overridden. A small on-premises model then reads the prompt and may raise the classification, but never lower what the user chose, so a router fooled by a crafted prompt cannot send confidential data to the cloud. If the model is slow, down or answers in the wrong format, the conversation is treated as confidential. The router must itself run on-premises, because it reads every prompt before anything is known about it.

Switchyard decides the model. Switchyard is NVIDIA's open-source routing proxy, written in Rust and published under Apache 2.0; it replaces NVIDIA's earlier LLM Router blueprint.[28] For each request it can ask a small judge whether a cheaper model is likely to solve the task, and send it to the strong model only if not. It also falls back to another model on errors and rate limits, translates between the OpenAI and Anthropic APIs, and logs every routing decision with its cost. It can use dedicated decision models, such as Jev, as judges. In the reference build, Switchyard holds one route per classification. The public and internal routes may choose between a local model and Claude. The confidential route contains on-premises models only. The hub's router picks the route, and Switchyard picks the model within it, so a mistaken Switchyard judgement can cost money but cannot move data across the boundary. Switchyard calls itself pre-alpha software that is not yet meant for production, so it belongs in the pilot rather than in a production commitment.[28] vLLM Semantic Router is a comparable open alternative.[27]

How a job runs in this cluster. Today the reference build runs on Docker Compose on a single host, and Kubernetes is not required to try it. In a shared cluster, each agent becomes a Deployment with one or more replicas. The agent opens its connection to the gateway, so the cluster exposes nothing. When the planning model asks for a contract to be read, the gateway sends the job down the DMS agent's connection. The agent reads the file in place. It then calls the worker model through the guardrail service, a normal in-cluster address, and checks the answer against its schema. Only the checked result goes back up. The OpenShell policy for that pod allows exactly three destinations: the gateway, the guardrail service and the document system. Anything else is blocked and logged, even if a malicious document persuades the agent to try.

Who gets the GPUs. The agent pods need no GPU; the models do. The GPU Operator installs drivers and exposes GPUs to Kubernetes, and can split one GPU into isolated slices (MIG) for small worker models. The scheduler then decides placement. KAI Scheduler, which NVIDIA publishes as open source, and the commercial Run:ai give each team a guaranteed GPU quota that it can exceed while others are idle. They also start a multi-pod model either completely or not at all (gang scheduling), and keep its pods close together in the network.[24] That is what makes a frontier-class model across 16 GPUs and a dozen small worker models share the same hardware. DGX Spark units can join as arm64 worker nodes for small models. Each container image must then exist for arm64, which is worth checking component by component.

Where the hybrid design wins. Its distinctive strength is the routing layer. A single platform can send public research to the cloud, internal work to whichever model is allowed, and confidential work to on-premises models only, with the decision made in code, logged and shown to the user. Types A and B are built around one provider's cloud, and type C around the organisation's own hardware. Each is strong in its own zone but has no natural place for the other. Because every component in E speaks an open interface (OpenAI-compatible models, MCP tools, outbound WebSocket agents), any model or agent can be replaced without touching the rest. Its cost profile is also attractive: the frontier model sees findings rather than documents, which cut cloud tokens by roughly an order of magnitude in the illustration in Section 7.

Where it falls short. As built, E is a reference design, not a product. It runs one hub with no high availability, uses a shared token rather than single sign-on, and has no per-team separation. Its agent protocol is its own rather than A2A. The router's accuracy has not been measured against a labelled set of real prompts. Every one of these gaps has a standard remedy (Table 2), but closing them is the work that type D represents, and it needs a platform team. The on-premises frontier model is also capital-intensive: a Kimi K3-class model needs two 8-GPU servers before the first prompt is answered.

Which to choose. For organisations with little sensitive data, a cloud assistant (A) is the fastest and cheapest route, and building anything else is hard to justify. For organisations already committed to one hyperscaler, its agent platform (B) with regional hosting covers most needs, provided the most sensitive work is kept out of scope. For organisations whose core data cannot leave the building, a turnkey private platform (C) is the safest start, accepting a gap in model quality. The hybrid design (E) fits the large middle ground: data of mixed sensitivity, a wish to use the best models where the rules allow it, and an IT department willing to run a gateway. In practice it is less an alternative to B and C than a way to combine them. A turnkey platform can host the on-premises tier, a hyperscaler or Claude can supply the cloud tier, and the routing layer decides which tier each conversation may reach.

12The challenges

None of this comes free, and the first obstacle is price. At $2,600 to $7,000, RTX Spark laptops cost more than Intel or AMD machines with dedicated NVIDIA graphics, as reviewers noted.[5] The premium pays off only for people who actually run large models locally. For office work alone it is hard to justify.

The second is that usable memory is not the number on the box. A 128 GB laptop that gives its GPU 64 GB cannot load an 80 GB model, so how the laptop maker splits memory must be checked before workloads are planned. The third is compatibility. Microsoft's x86 emulation handles most applications well, and reviewers found emulated software felt native.[5] But kernel drivers, VPN clients, endpoint security agents and specialised business software still have to be tested one by one, and Android Studio's emulator is a known gap.[16]

For IT departments, the challenges are mostly operational. Model files of 4 to 60 GB per device have to be distributed, versioned, licence-checked and retired, a new job for endpoint management. A local agent that can read files and run tools is a new attack surface and needs the controls of any privileged software: least privilege, signed tools and logging. Microsoft and NVIDIA describe new Windows security primitives for on-device agents, but they are new and unproven at scale.[17] Finally, local inference is not free; it is prepaid. Hardware, power and battery wear replace the token bill, and the comparison has to be made over the life of the device, on real workloads.

13Conclusion

RTX Spark makes the laptop a serious place to run AI. For the individual, the case rests on privacy, offline work and the absence of a per-token bill. A 64 GB configuration is the practical sweet spot for capable 20–35-billion-parameter models; 128 GB makes sense for developers who need 120-billion-parameter models, once the GPU memory share is confirmed.

For organisations, the larger opportunity lies in architecture rather than hardware. Treated as each user's own workstation in a hybrid system, the laptop handles what fits on it, on-premises GPU servers take the confidential work that is too large for a laptop, and a frontier model does only the planning it is best at: in the cloud for most work, or on the organisation's own GPU servers where the data rules demand it. A gateway that separates control from data, routes by data classification and logs every decision turns that division of labour into something an auditor can verify.

The sensible way in is small. Start with ten users and two use cases where data must not leave the organisation. Test the security stack under Arm. Measure accuracy, cloud tokens saved and battery life against a cloud-only baseline. Then build the central gateway and the approved model catalogue, and scale by use case rather than by device count.
