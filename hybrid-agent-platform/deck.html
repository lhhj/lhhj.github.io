The problem

Our data has three sensitivities. Most platforms serve one.

Public

Market research, product news, public documentation. Any model may see it, and the best cloud models give the best results.

Internal

Contracts, customer lists, budgets, system status. May use approved cloud models, but must not reach public web agents.

Confidential

HR cases, pay, health, personal ID numbers, client-privileged material. Must stay on our own models and hardware.

Cloud assistants cover the first column well; private platforms cover the third. The target design is one platform that routes each conversation to the right column, in code, with a log.

Hybrid agent platform03 / 13
One request, end to end

How a conversation moves through the platform

  1. ClassifyRules, then a small on-prem model, rate the prompt. They can raise the level the user set, never lower it.
  2. RouteThe policy picks the Switchyard route for that level; Switchyard picks the model inside it. Confidential routes hold on-prem models only.
  3. PlanThe chosen model sees only permitted tools and decides which agents to call, in parallel where it can.
  4. WorkEach job goes down the agent's own outbound connection. The agent reads data in place with a local model.
  5. ReturnOnly a schema-checked result goes back up. Every step is logged and shown in the traffic view.

No inbound ports

Agents and the model relay dial out. The cluster exposes nothing.

Policy in code

Tool calls are re-checked against the allowed list, so a misled model cannot reach a hidden tool.

Findings, not files

The planning model receives structured results, about 90 tokens per document instead of 4,000.

Hybrid agent platform04 / 13
The local router

A small model decides where a conversation may go

Rules first

Personal ID numbers, pay, HR, health and "confidential" markings raise the level. No model can override them.

Raise only

The router model may make a conversation stricter, never looser. A prompt crafted to fool it cannot unlock the cloud.

Fail closed

A slow, failed or malformed answer means confidential: the work stays on our own models.

Then optimise

Simple requests go to a small local model; complex ones to the best frontier model the level allows.

Runs on-prem because it reads every raw prompt. Built into the reference hub today with Qwen 2.5 3B in Ollama. Which model answers is then left to NVIDIA NeMo Switchyard, within the route the level allows.

Our router sets the boundary. Switchyard picks the model.

How sensitive is it?Hub routerRules, then a small on-prem model; raise-only, fail closed, logged

Which model answers?SwitchyardA local judge estimates whether the cheaper model can solve it; otherwise the strong model answers
What if a model fails?SwitchyardRetries, cooldown, fallback to the other target in the same route
What did it cost?SwitchyardPer-request routing log with model and cost; live counters for benchmarking

Safe by construction

A wrong Switchyard judgement can cost money. It cannot move data across the boundary.

Harness ready

Switchyard speaks the OpenAI and Anthropic APIs, so Claude Code can run on an on-prem route.

Pre-alpha

v0.3.0, Apache 2.0, "not for production use". Pilot it; don't build commitments on it yet.

Sizing the GPU tier

The planner is the expensive part

~2 TB

Kimi K3-class planner

2.8T parameters, 1.56 TB of weights in MXFP4. Two 8-GPU H200 servers; one HGX H200 system is priced at $320–420k.

1 node

300–700B open models

GLM and DeepSeek class fit one 8-GPU H200/B200 server, at some cost in planning quality.

20–120B

Workers

Extraction, OCR and embeddings on MIG slices or DGX Spark nodes. This is where most documents are read.

A pragmatic start keeps the planner in the cloud for public and internal work, and uses a single-node open model for confidential planning until volumes justify more.
