Sovereignty-aware routing for hybrid agent systems: a reference architecture and an evaluation of a raise-only local router

Leif Howalt Elgaard Høj · Danoffice IT · Blog post

AbstractOrganisations that adopt large language model (LLM) agents handle data of mixed sensitivity, yet most deployment options serve a single trust zone: a provider's cloud or the organisation's own hardware. We describe a hybrid reference architecture in which a gateway classifies each conversation before any model sees it, restricts it to models and agents in permitted zones, and lets on-premises agents read data in place over outbound-only connections, returning schema-checked findings instead of documents. Classification is made by a local router that combines fixed rules with a small on-premises model under three invariants: it may only raise a classification, it fails closed, and policy is enforced on every tool call. Model choice within a permitted zone is delegated to NVIDIA NeMo Switchyard. On a labelled set of 72 English and Danish prompts, rules alone reached 58.3% accuracy and caught 12 of 24 confidential prompts; with the router model, two runs gave 69.4% and 68.1% accuracy and caught 15 and 14 of 24. Most remaining misses were rated internal, but one prompt in the second run was rated public, so a policy that reserves the cloud for public work reduced exposure without removing it. In a first measurement on 40 contract readings, sending findings instead of documents cut cloud input tokens by 81%; the reference extraction path returned only 5% of the facts correctly, for reasons traced to its implementation, so the accuracy of the hybrid path is not yet established.

1 Introduction

Enterprise use of LLM agents sits between two kinds of offering. Cloud assistants and hyperscaler agent platforms give access to the strongest models, but process prompts and retrieved documents in the provider's infrastructure. Private AI platforms keep data on the organisation's own hardware, but limit it to the open-weight models that hardware can serve. Most organisations hold data of both kinds, and of a third kind in between: public research, internal business records, and confidential material such as personnel cases, pay and health data. A platform built for one zone either over-exposes the confidential tier or under-serves the public one.

This report describes a hybrid design that treats the trust zone as a property of each conversation rather than of the platform. It makes three contributions. First, a reference architecture in which on-premises agents work beside the data and connect outwards to a gateway, so that the planning model receives findings rather than documents and no inbound network path is required. Second, a local router whose safety rests on invariants enforced in code rather than on model accuracy. Third, an evaluation of that router on a labelled set of English and Danish prompts, together with a reference implementation and test suite.

2 Related work

Gateways and protocols. AI gateways such as LiteLLM, Envoy AI Gateway and agentgateway expose one OpenAI-compatible interface across providers and add keys, quotas and fallbacks; several also proxy the Model Context Protocol (MCP) for tools and the A2A protocol between agents9,1. They route on declared attributes (model name, cost, availability) rather than on the content of a request.

Learned routing. RouteLLM showed that a router trained on preference data can send a large share of queries to a cheaper model with limited loss in quality2. vLLM Semantic Router applies small classifiers for domain, personal data and jailbreak attempts before choosing a model5, and NVIDIA NeMo Switchyard asks a judge model whether a weaker model can solve a request, falls back between targets and logs each decision6. These systems optimise cost and quality. They are not designed to guarantee that a misjudged request stays inside a trust boundary, which is the property this work adds.

Agent security. Indirect prompt injection, in which instructions hidden in retrieved content take over an agent, is a well-documented risk3,4. NVIDIA's OpenShell runtime enforces network and file policy outside the agent process7, and NeMo Guardrails screens prompts and outputs8. The design here is complementary: it limits what a compromised model can reach by construction.

3 Architecture

The system has four trust zones: the cloud, Hugging Face Spaces, the organisation's network, and the organisation's GPU tier. Every model provider and agent declares its zone. A classification policy maps each of three levels to the zones it may reach: public work may use any zone, internal work excludes public web agents, and confidential work is restricted to on-premises models and agents.

Agents are small processes that run next to a data system, expose typed tools, and open a single WebSocket connection out to the gateway. Jobs travel down that connection and results travel back, so neither agents nor GPU servers need an inbound port. An agent reads documents with a local model and returns only a result that passes a strict schema (extra fields rejected), so a planning model in the cloud sees a few hundred tokens of findings per document rather than the document itself. The same mechanism lets a gateway in the cloud use a frontier-class model on-premises: a relay agent beside the GPU server forwards chat-completion requests over its outbound connection.

Model choice within a permitted zone is delegated to NVIDIA NeMo Switchyard6. The gateway defines one Switchyard route per classification. The routes for public and internal work may choose between a small local model and a cloud frontier model, using a local judge; the route for confidential work contains on-premises targets only. Switchyard also translates between the OpenAI and Anthropic APIs, so an agent harness such as Claude Code can use the same routes.

4 The local router

The router decides how sensitive a conversation is before any model sees it. It has two layers. Fixed rules, regular expressions for personal identification numbers, pay, personnel cases, health terms and explicit markings, run first. A small on-premises model then reads the prompt and returns a classification, a complexity estimate and a short reason in JSON. The router runs on-premises because it reads raw prompts before anything is known about them; a router endpoint declared to be in the cloud is refused at start-up.

The design does not assume the router model is accurate or honest. Its safety rests on three invariants, each enforced in the gateway's code and covered by automated tests:

  1. Raise only. The final classification is the strictest of the user's choice, the rules and the model. A router model fooled by a crafted prompt can make a conversation stricter, which costs capability, but cannot make it looser, which would cost confidentiality.
  2. Fail closed. A router model that times out, errors or answers outside the expected format sets the classification to confidential.
  3. Enforce on every call. The planning model is offered only the tools its classification permits, and every tool call it makes is checked again against that list, so a model that names a hidden tool, by error or under injection, is refused.

A fourth property applies at the edge of the system. When an external harness hands a task to the gateway over MCP, and the harness's own model runs in the cloud, answers to conversations classified as confidential are not returned to it; the harness receives only the routing decision.

5 Implementation

The reference implementation is a Python gateway (FastAPI), an agent SDK, an on-premises document agent with a schema gate, a model relay, and a research agent deployable as a Hugging Face Space, about 2,200 lines in total. It runs with Docker Compose on a single Windows or Linux host, with Ollama serving the local models; optional profiles add vLLM for an on-premises frontier model and Switchyard. Fifty-five automated tests cover the invariants above, the relay, reasoning passthrough for models that return a separate reasoning field, and the Switchyard integration, in which Switchyard's own engine is run against stand-in models. All of these tests use stand-in models; none exercises a real local model.

6 Evaluation

6.1 Router classification

Data. The evaluation set has 72 prompts written by the author, 24 per level, 41 in English and 31 in Danish. Labels follow the router's definitions: public for general knowledge, internal for company information not about identifiable people, confidential for personal data, personnel matters, health, pay and material marked confidential. Twenty-seven prompts are marked hard: they contain no keyword any rule matches (for example “Draft a warning letter to Jens about his repeated absence”), or they contain a sensitive keyword in a public question (“What is a framework contract under EU procurement rules?”).

Method. Each prompt is sent to the gateway's dry-run endpoint with the user's classification set to public, the most permissive start, so the router alone is measured. Two passes are made: rules only, and rules plus the router model (qwen2.5:3b). The primary metric is the share of confidential prompts caught; a missed confidential prompt is one that could have reached a cloud model. Secondary metrics are accuracy, over-classification (stricter than the label, which costs capability) and latency.

Results. Rules alone classified 58.3% of prompts correctly and caught 50.0% of confidential prompts. They were accurate on plain prompts (93.3%) and, by construction of the set, on none of the hard ones. Adding the router model (qwen2.5:3b, a 3-billion-parameter instruction model run on CPU or a consumer GPU through Ollama) raised overall accuracy from 58.3% to 69.4% and the share of confidential prompts caught from 50.0% to 62.5%. On the hard prompts, which contain no keyword a rule could match, accuracy rose from 0.0% to 40.7%. Median router-model latency was 386 ms (95th percentile 489 ms) on the author's workstation. In 3 cases the router model's answer was not in the expected format and the fail-closed rule set the classification to confidential; all of these were public prompts, so the cost was capability, not exposure.

Second run. The evaluation was repeated on 6 November, after the model server's context length had been raised to 8,192 tokens so that whole contracts fit for Section 6.3. Accuracy was 68.1% and 14 of 24 confidential prompts were caught. One confidential prompt, p56, was rated public; in the first run it had been rated internal. Seven of the 72 verdicts differed between the runs although the temperature was zero in both. Median router-model latency rose to 2,033 ms (95th percentile 3,232 ms). Again 3 public prompts fell back to confidential, two of them the same prompts as in the first run because the model's reply could not be parsed. Rule revision. The first run of the rules missed four plain confidential prompts because the patterns did not cover inflected forms (“medical records”, Danish “personalesagen”, “fyringen”, “fortroligt”). The patterns were revised to match inflections of the words they already listed, without adding the vocabulary of the hard prompts, and the figures above are for the revised rules. Because the revision was made on the evaluation set, the rules-only figure for plain prompts is optimistic.

6.2 What a miss means: exposure under two policies

Whether a misclassified prompt can reach a cloud model depends on the policy, not only on the router. Under the default policy, internal work may use cloud models, so a confidential prompt rated internal is exposed. Under a strict policy, only public work may use the cloud, so a confidential prompt is exposed only if it is rated public. Table 2 applies both policies to the predictions of each run.

The router model's errors are asymmetric: it rarely rates sensitive material as public. In the first run it never did, and the first version of this report concluded that the strict policy removed cloud exposure on this set. The second run does not support that conclusion. One prompt was rated public, and zero misses in 24 prompts is in any case compatible with a true miss rate of up to 14% (95% Wilson interval). The strict policy reduces exposure, at the price of keeping internal work and the over-classified public prompts on on-premises models; it does not remove it. The reference build ships with the default policy, under which 37.5% and 41.7% of the confidential prompts could have reached a cloud model as prompt text. Rules alone lack even the asymmetry, because a prompt without keywords stays at the user's starting level.

6.3 Cloud tokens

For a task that reads d documents of tdoc tokens with a prompt of p tokens, a cloud-only design sends d·tdoc + p input tokens to the cloud. In the hybrid design a fraction f of tasks is planned in the cloud, and those send d·tf + p, where tf is the size of the checked findings. With d = 3, tdoc = 4,150, tf = 210, p = 2,000 and f = 0.4 (confidential and simple tasks kept local), cloud input falls from 14,450 to 1,052 tokens per task on average, a reduction of 93%. With an on-premises planner and only public research in the cloud (f = 0.1) the reduction is 98%. These figures are analytic; the parameters are the first to measure in a pilot.

First measurement. On 6 November the same extraction tasks were run both ways: with the contracts pasted into the cloud model's context, and through the gateway with the on-premises agent reading them. The corpus is 20 synthetic supplier contracts of about 2,900 words, about 5,950 cloud input tokens each, with known answers for four facts per contract and distractor clauses. Tasks hold 1, 2, 5 or 10 contracts; a 20-contract task did not complete. The cloud model was Claude Sonnet 5.5 and the local reader qwen2.5:3b.

The token reduction has the size the model predicts and grows with the number of documents; at one document per task the planning overhead leaves 29%. The accuracy is not a result about the design. It traces to three defects in the reference extraction code. The local model was not given the field definitions that the cloud model received. Three of the four scored fields were optional in the schema and the model left them out, so that all 41 accepted findings carried no notice period and no renewal term. And requests retried behind two model slots produced waits of up to an hour. The gate accepted these findings because it checks the form of a finding, not whether it is true. The defects are repaired in the code and the measurement will be repeated. Until then the accuracy of a hybrid path with a 3-billion-parameter reader is an open question, and a token saving without it has no value.

7 Discussion and limitations

The results support the division of labour in the design. Fixed rules are fast and predictable but cannot recognise sensitivity that is expressed without keywords, which is common in personnel and health matters. A small local model recovers part of that gap. It did not, in this evaluation, recover enough to serve as the only safeguard under the default policy: a 3-billion-parameter model still rated a substantial share of confidential prompts as internal. Two conclusions follow. The classification a user or a data source sets must remain the primary control, with the router as a second line that can only add caution. And where confidential data is common, the strict policy, cloud models for public work only, turns the router's asymmetric errors into a safer default, though not, as the second run showed, a safe one. A larger or fine-tuned router model, or a dedicated classifier, may allow the default policy; that is an empirical question for a larger evaluation set.

The evaluation has clear limits. The prompt set is small, written and labelled by one person, and partly constructed to be hard; it measures relative behaviour rather than expected accuracy on real traffic. The rules were revised on the same set. Only one router model was tested. The reference implementation runs one gateway without high availability, single sign-on or per-team separation, and its agent protocol is its own rather than A2A. Switchyard describes itself as pre-alpha software. Running a frontier-class model on-premises is capital-intensive: Kimi K3, at 1.56 TB of weights, needs roughly two 8-GPU H200 servers10, and sharing such hardware between teams calls for Kubernetes scheduling of the kind provided by KAI Scheduler or Run:ai11. Results were not stable across two runs of the same router model, so a single run should not be reported as a property of the design. The schema gate constrains the form of a finding, not its truth or its information content: one finding can carry about 123 bits, and a test finding that hid a ten-digit number in the clause-reference field passed the gate. The automated tests use stand-in models, and the first test with a real local reader was the measurement in Section 6.3.

Natural next steps are an evaluation on a few hundred prompts drawn from real use and labelled by data owners, a comparison of router models including dedicated classifiers, sandboxing agents with OpenShell, repairing and repeating the token measurement, and checking each extracted value against the passage it cites before it leaves the organisation.

8 Conclusion

Treating the trust zone as a property of each conversation lets one platform use frontier cloud models where data rules allow and the organisation's own GPUs where they require it. The design keeps the decision that protects data deterministic and logged, and lets models make only the decisions whose errors are recoverable: a small local router may raise, but never lower, a classification, and a routing proxy chooses among models only within the zones that classification allows. The first measurements qualify the picture rather than the principle: the router's errors varied between two runs, a strict policy lowered exposure without removing it, and the extraction path has yet to show usable accuracy with a small local model.
