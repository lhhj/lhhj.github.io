Frontier models where allowed, our own GPUs where required

Leif Howalt Elgaard Høj · Danoffice IT · Technical report

Most conversations I have with customers about AI agents end up at the same question: can we use the best models without sending our most sensitive data to someone else's cloud? Usually the answer offered is a choice. Pick the cloud and get the best models, or pick your own hardware and keep the data. I wanted to see whether a single platform could make that choice per conversation instead.

Updated 10 November 2026I ran the measurements again, and added one I had only modelled. One claim in the first version of this post did not hold up, and the first real test of the document agents went badly. Both are described below, with what I am doing about it.

The idea

An organisation's data is not one thing. Some of it is public: product news, research, documentation. Some is internal: contracts, customers, budgets. And some is confidential: personnel cases, pay, health. Each kind can safely go to a different set of models.

So the platform starts every conversation by asking how sensitive it is. A small router on-premises reads the prompt, checks it against fixed rules and a small local model, and labels it public, internal or confidential. The gateway then only lets that conversation reach models and agents in permitted places. Confidential work stays on the organisation's own models. Public research can use a frontier model in the cloud, or a research agent running as a Hugging Face Space.

The agents themselves sit next to the data, in the document system or the ERP, and connect out to the gateway. They read documents locally and return short, checked findings, so a cloud model that plans the work sees a few hundred tokens per document instead of the document. In a first measurement that removed 81% of the cloud input, and 92% for tasks with ten documents. Whether the answers were any good is a separate matter, and I come to it below.

Making a model-based router safe

Putting a model in charge of deciding what is confidential sounds risky, and it would be if the model's answer were trusted. The router is built so that it does not have to be. It may only make a conversation stricter, never looser. If the router model is slow, down or answers nonsense, the conversation is treated as confidential. And every tool the planning model calls is checked again in code, so a model that has been tricked by a hidden instruction in a document still cannot reach a tool it was not offered.

Which model then answers is a different question: a cheaper local one, or a frontier model. That I leave to NVIDIA's new open-source router, NeMo Switchyard. It gets one route per classification, and the confidential route only contains on-premises models. A wrong choice by Switchyard can cost money. It cannot move data across the boundary.

What I measured

I wrote 72 prompts in English and Danish, 24 for each level, and labelled them. About a third are deliberately hard: confidential requests without any obvious keyword, or public questions that happen to contain words like “salary” or “contract”.

Rules alone caught 50% of the confidential prompts. Every one they missed was a prompt with no keyword to match, such as a warning letter about someone's absence or a question about who is on sick leave. With a 3-billion-parameter model added on-premises, the router caught 15 of 24 in a first run and 14 of 24 in a second, and overall accuracy was 69% and 68%. With only 24 confidential prompts that difference from the rules is within the noise.

That is not good enough to be the only safeguard, and I want to be clear about that. In the first run the misses looked interesting: the small model rated none of the confidential prompts as public. The ones it missed, it rated internal. I wrote here that if an organisation lets only public work go to the cloud, none of the confidential prompts in the set would have left the building.

That claim did not survive a second run. The next day, with one setting changed on the model server, the same model rated one confidential prompt as public: “Draft a warning letter to Jens about his repeated absence.” Seven of the 72 verdicts changed between the two runs. A strict policy still lowers the exposure a great deal, from 12 prompts to 1. It does not make it zero, and 24 prompts could never have shown that it did. Under the platform's default policy, where internal work may also use cloud models, 9 and 10 of the 24 could have reached one.

The lesson I take is the one the design already pointed at: the classification a user or a data source sets has to be the primary control. A label on the document is worth more than a model's guess about the prompt. The router can only add caution.

The set is small and I wrote it myself, so treat the numbers as a first measurement rather than a benchmark. The technical report has the details, the confusion matrices and the limitations.

The first token measurement

I also ran the test I had only modelled before: the same contract questions answered two ways. Once with the contracts pasted into the cloud model, and once through the platform, with the on-premises agent reading 20 synthetic contracts using a small local model and passing back checked findings.

The token saving was real: 81% less cloud input over 40 contract readings. The answers were not. The hybrid path got 5% of the facts right, against 99% for the cloud model reading the contracts itself, and took 16 minutes per task instead of a few seconds.

When I looked into it, the fault was in my own extraction code more than in the idea. The local model was never told what the fields meant, while the cloud model was. Fields the model left out were quietly filled in as “not stated”, and the check at the boundary accepted that, because it checks the shape of a finding and not whether it is true. And a retry setting turned a queue of two into half-hour stalls. I have repaired all three and will run it again. Until then I cannot say whether a 3-billion-parameter model is a good enough reader, and a token saving without correct answers is worth nothing.

How it runs

The reference build runs on a single Windows PC with Docker Desktop: the gateway, the router, an on-premises agent and a local model start together, and Claude Code, Claude Desktop or Cursor can connect to it as tools. The same build scales out to agents beside real systems and a frontier-class model on the organisation's own GPU servers. The code is not public yet; if you would like a demo, get in touch.

What's next

The obvious next step is a pilot with real data owners: a few hundred real prompts labelled by the people responsible for the data, agents beside a real document system, and the token savings measured together with accuracy. Before that, I owe a rerun of the token test with the repaired code. If your organisation has data that cannot leave the building but would benefit from frontier models elsewhere, I would like to hear from you.
