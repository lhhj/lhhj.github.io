Frontier models where allowed, our own GPUs where required

Leif Howalt Elgaard Høj · Danoffice IT · Technical report · Code

Most conversations I have with customers about AI agents end up at the same question: can we use the best models without sending our most sensitive data to someone else's cloud? Usually the answer offered is a choice. Pick the cloud and get the best models, or pick your own hardware and keep the data. I wanted to see whether a single platform could make that choice per conversation instead.

The idea

An organisation's data is not one thing. Some of it is public: product news, research, documentation. Some is internal: contracts, customers, budgets. And some is confidential: personnel cases, pay, health. Each kind can safely go to a different set of models.

So the platform starts every conversation by asking how sensitive it is. A small router on-premises reads the prompt, checks it against fixed rules and a small local model, and labels it public, internal or confidential. The gateway then only lets that conversation reach models and agents in permitted places. Confidential work stays on the organisation's own models. Public research can use a frontier model in the cloud, or a research agent running as a Hugging Face Space.

The agents themselves sit next to the data, in the document system or the ERP, and connect out to the gateway. They read documents locally and return short, checked findings, so a cloud model that plans the work sees a few hundred tokens per document instead of the document. In my token model that removes over 90% of the cloud input for document-heavy tasks.

Making a model-based router safe

Putting a model in charge of deciding what is confidential sounds risky, and it would be if the model's answer were trusted. The router is built so that it does not have to be. It may only make a conversation stricter, never looser. If the router model is slow, down or answers nonsense, the conversation is treated as confidential. And every tool the planning model calls is checked again in code, so a model that has been tricked by a hidden instruction in a document still cannot reach a tool it was not offered.

Which model then answers is a different question: a cheaper local one, or a frontier model. That I leave to NVIDIA's new open-source router, NeMo Switchyard. It gets one route per classification, and the confidential route only contains on-premises models. A wrong choice by Switchyard can cost money. It cannot move data across the boundary.

What I measured

I wrote 72 prompts in English and Danish, 24 for each level, and labelled them. About a third are deliberately hard: confidential requests without any obvious keyword, or public questions that happen to contain words like “salary” or “contract”.

Rules alone caught 50% of the confidential prompts. Every one they missed was a prompt with no keyword to match, such as a warning letter about someone's absence or a question about who is on sick leave. With a 3-billion-parameter model added on-premises, the router caught 62%, and overall accuracy rose from 58% to 69%. The model answered in a median of 0.4 seconds on my workstation.

62% is not good enough to be the only safeguard, and I want to be clear about that. But the misses were interesting: the small model rated none of the confidential prompts as public. The ones it missed, it rated internal. So if an organisation lets only public work go to the cloud, none of the confidential prompts in the set would have left the building. The price is that internal work stays on local models too. That is a policy choice the platform makes explicit, rather than a hope about model accuracy. The classification a user or a data source sets stays the primary control; the router can only add caution.

The set is small and I wrote it myself, so treat the numbers as a first measurement rather than a benchmark. The technical report has the details, the confusion matrices and the limitations.

Try it

The code is open source. On a Windows PC with Docker Desktop it starts in three steps: start Docker, double-click start-local.cmd, and double-click connect-harness.cmd to connect Claude Code, Claude Desktop or Cursor. run-eval.cmd reruns the evaluation on your own machine, and the prompt set is a plain file you can extend with your own examples.

What's next

The obvious next step is a pilot with real data owners: a few hundred real prompts labelled by the people responsible for the data, agents beside a real document system, and the token savings measured rather than modelled. If your organisation has data that cannot leave the building but would benefit from frontier models elsewhere, I would like to hear from you.
